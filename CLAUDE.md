# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Tribbae is a family idea-management app (links, recipes, activities, gifts, events) with three parts that share one REST API:

| Part | Stack | Dir |
|------|-------|-----|
| Backend | Go + gRPC + grpc-gateway (REST) + MongoDB | `backend/` |
| Web | React 19 + TypeScript + Vite + Tailwind 4 | `frontend/` |
| Android | Kotlin Multiplatform + Jetpack Compose (package `com.linkkeeper.app`) | `composeApp/` |
| AI | Ollama (local model, Docker) | `backend/internal/ai/` |

**Core rule (from `.kiro/steering/`): every user-facing feature must be implemented on both clients (web + Android).** Docs, comments and UI strings are in French; gRPC error messages are in English.

## Commands

Task runner is [Task](https://taskfile.dev) (`Taskfile.yml` at the root).

```bash
task dev                # Ollama (Docker) + backend + frontend in parallel
task dev:docker         # Everything via docker-compose.local.yml
task backend            # go run ./cmd/server — NOTE: loads backend/.env.example, not .env
task backend:proto      # buf generate (run after editing any .proto)
task frontend:dev       # Vite on :5173, proxies /v1 -> localhost:8080
task build              # Android debug APK (./gradlew :composeApp:assembleDebug)
task run                # install + launch on connected device
task check              # ./gradlew check (Android lint + tests)
task seed               # k6 run scripts/seed-data.js (test data)
```

Backend (from `backend/`):
```bash
go build ./...
go test ./...
go test ./internal/link -run TestName -v   # single test
```
Backend tests (`internal/{link,folder,follow,comment}/*_test.go`) hit a real MongoDB at `mongodb://localhost:27017`, create a throwaway `tribbae_test_<id>` DB, and **skip** (not fail) if Mongo isn't reachable. Some use `gopter` property-based testing.

Frontend (from `frontend/`): `npm run build` (runs `tsc -b` then `vite build` — this is the type check CI runs), `npm run lint`.

CI (`.github/workflows/test.yml`): `go build` + `go vet` + `go test -race` (with a MongoDB service) + `govulncheck` for backend, `npm ci && npm run lint && npm run build` for frontend, `./gradlew assembleDebug` for Android. `release.yml` triggers on `v*` tags (APK + Docker images).

## Git workflow

- **One PR per topic.** Never commit on `main`: branch from an up-to-date `main`, keep the branch to a single subject (a fix, a feature, a CI change…), and open a separate PR for anything unrelated found along the way. A CI fix and a dependency bump are two PRs, not one.
- Branch names: `<type>/<short-kebab-description>`, e.g. `fix/govulncheck-go-patch`, `feat/tribe-invitations`, `ci/mongo-9`.
- **Commits follow [Conventional Commits](https://www.conventionalcommits.org/)**: `<type>(<scope>): <description>`, description in English, imperative, lowercase, no final period.
  - Types: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `style`, `build`, `ci`, `chore`, `revert`.
  - Scopes (optional): `backend`, `frontend`, `android`, `ai`, `proto`, `seo`, `ci`, `docker`, `deps`, or a backend domain (`link`, `folder`, `tribe`…).
  - Breaking change: `!` after the type/scope and a `BREAKING CHANGE:` footer.
  - Examples: `fix(ci): always install the latest go 1.26 patch`, `feat(tribe)!: require confirmation before sharing content`.
- PRs are squash-merged, so **the PR title must itself be a Conventional Commit** (it becomes the commit on `main`). The PR description says what changed, why, and how it was tested.
- Commits must be authored and signed by the `jplanckeel` account (`Jérémy PLANCKEEL <jeremy.planckeel@outlook.com>`, GPG key `49D1339A1DA8FB47`), set in this repo's local git config. Never pass `--no-gpg-sign` or override the identity, never rewrite published history and never force-push `main`.
- **Every commit needs a DCO sign-off** (`Signed-off-by: Jérémy PLANCKEEL <jeremy.planckeel@outlook.com>`): the DCO app blocks any PR containing a commit without it. Always commit with `git commit -s` (a local `prepare-commit-msg` hook also adds it). GPG signing and sign-off are two different things; both are required.

## Backend architecture

- `cmd/server/main.go` wires everything: Mongo connect → `db.EnsureIndexes` → `auth.EnsureAdminAccount` → services → gRPC server on `GRPC_PORT` (9090) → grpc-gateway mux on `PORT` (8080) dialing back into the gRPC server.
- Each domain in `internal/<domain>/` (auth, link, folder, child, follow, comment, admin, ai) has `service.go` (business logic + Mongo access via `bson.M`) and `handler.go` (gRPC server implementing the generated interface). Services receive their `*mongo.Collection`s from `main.go`.
- **API surface is defined in `backend/proto/tribbae/v1/*.proto`** with `google.api.http` annotations. Generated Go, gateway and OpenAPI code lives in `backend/gen/` and **is committed** (needed for the Docker build) — regenerate with `task backend:proto`, never hand-edit.
- Auth: `internal/interceptor` is a gRPC unary interceptor that validates `Authorization: Bearer <JWT>` and puts the user ID in the context. Endpoints that work unauthenticated must be added to the `publicMethods` map there (token is then optional) — read endpoints for public content (`GetLink`, `GetFolder`, `ListLinks` with a folder, comments) are public and rely on the service-level visibility checks. Admin-only methods are guarded by `UnaryAdminAuth`.
- Some routes bypass grpc-gateway and are plain `net/http` handlers wrapped in `main.go`: `POST /v1/ai/generate` (`withAI`), `GET /v1/links/preview` (Open Graph extraction, `withPreview`), and the GDPR routes `GET /v1/account/export` / `POST /v1/account/delete` (`withAccount`, `internal/account`; deletion requires the password, is rate-limited like login, and erases everything the account owns while keeping other users' ideas — **a new collection holding user data must be added to `account.Service.Export` and `Delete`**). `auth.ValidateToken` rejects tokens of deleted accounts. Privacy policy: `frontend/src/pages/Privacy.tsx` (`/confidentialite`; editor and host placeholders to fill), linked from sign-up on both clients. Android `LinkViewModel.signOut()` also wipes the offline cache. New non-proto HTTP routes follow the same wrapper pattern.
- Photos (`internal/photo`, `withPhotos`): `POST /v1/photos` (signed in, body = the raw image, ≤ 12 MB, own rate limit, outside the 1 MB `MaxBody`) decodes JPEG/PNG/WebP only, turns it upright (EXIF orientation), shrinks it to 1600 px and re-encodes it as JPEG (no metadata, so no GPS), stores it in MongoDB GridFS (bucket `photos`, owner in `metadata.owner_id`, file name = random 128-bit token) and answers `{url}` built from the request host (`https://tribbae.fr/v1/photos/<token>` in prod), which becomes the idea's `imageUrl`. `GET /v1/photos/<token>` is public and cached forever. `RunCleanup` deletes photos older than a day that no idea (`image_url`) or folder (`banner_url`) cites. Clients shrink before sending: web `lib/photo.ts` (`usePhotoUpload`) + `components/PhotoUpload.tsx`; Android `ImagePickerHelper` (copy in `filesDir/images`, upright, 1600 px) then `LinkViewModel.uploadLocalPhoto` when the idea is saved, and `uploadPendingPhotos` after each sync for ideas still holding a `file://` path (offline or created before uploads existed).
- The site lives on `https://tribbae.fr` (`SITE_URL`: canonical URLs, sitemap, email and folder-share links). `httpx.CanonicalHost` redirects everything requested on `REDIRECT_HOSTS` (old domain `tribbae.bananaops.cloud`, `www.tribbae.fr`) to it (301 for GET/HEAD, 308 otherwise), API included; Traefik routes all three names. The admin account email `tribbae@bananaops.cloud` is an account identifier and stays as is.
- In production a single image (root `Dockerfile`) serves the built frontend from `/public` (`STATIC_DIR` to override); anything under `/v1/` goes to the API. The SPA fallback goes through `internal/seo`: for each URL it replaces what lies between `<!--seo:head-->` markers in `frontend/index.html` with that page's head (title, description, canonical on `SITE_URL`, Open Graph, schema.org JSON-LD: Recipe/Event/Book/CollectionPage/FAQPage/BreadcrumbList) and fills `#root` with equivalent plain HTML, so search engines and AI crawlers that don't run JS see real content. Only anonymously visible content is rendered (same rules as a visitor without account); unknown/private ideas get 404 + noindex, private screens noindex, legacy URLs 301. It also serves dynamic `/sitemap.xml` (with images) and `/llms.txt`. The client mirrors head tags with `components/Seo.tsx` (every page renders one; it removes the server's `data-seo` tags on mount). The FAQ lives in `frontend/public/faq.json`, read by both `pages/Faq.tsx` and the server (FAQPage). Likewise the « À propos » page (`/a-propos`) lives in `frontend/public/about.json`, read by `pages/About.tsx` and the server (AboutPage, sitemap, llms.txt); Android opens it in the browser from the profile, like the privacy policy. Category intros are duplicated in `seo/categories.go` and `lib/categories.ts`.
- JSON is camelCase (protojson); enums serialize as names, e.g. `LINK_CATEGORY_RECETTE`.
- Tribe (`internal/tribe`, `tribe.proto`): accounts of one family share everything (ideas, folders, children). `tribe.Service.Peers(userID)` = the user + members with `sharing=true`; it is injected via `SetTribePeers` into the link, folder and child services and every ownership check must go through it (`isPeer`/`ownedByTribe`), never `owner_id == userID` alone. Joining is by invitation only (`internal/tribe/invitations.go`, `tribe_invitations`): `AddTribeMember` emails `SITE_URL/invitation#<token>` (hashed token, 7 days, one per tribe and address, resend after 10 min, members + pending ≤ 12) and answers the same whether the address has an account or not; `AcceptTribeInvitation` requires the signed-in account to use the invited address (the link proves it receives that inbox), `GetTribeInvitation` is public. A new member sees the tribe immediately but their own content joins only after they confirm (`sharing`). Web `pages/Invitation.tsx` (token kept in sessionStorage while signing in), Android `ui/InvitationDialog.kt` + `MainActivity.extractInviteToken`. Publishing (idea or folder visibility, moving an idea into a public folder) stays author/owner-only. One tribe per account (unique index on `members.user_id`); without a tribe document the tribe is virtual and named after the account. Ideas are always signed with the author's account name; the tribe name is only for « La tribu … » (home, Ma tribu). Clients mirror the peer set (web `useMyData().peers`, Android `LinkViewModel.isTribePeer`).
- Emails (`internal/mail`): transactional emails go through the Brevo API (`BREVO_API_KEY`, `MAIL_FROM`, `MAIL_FROM_NAME`; without a key they are only logged). `mail.Mailer` renders French HTML + text bodies from `internal/mail/templates/` (embedded; table layout + inline styles following the « Emails Tribbae » mockup, since mail clients ignore flexbox/SVG; logo and icons are PNGs in `frontend/public/email/`, served from `SITE_URL/email`; user input escaped) and sends in the background — a failed email never fails the user action, and logs carry only the email type, never the address. Services get it through small `Notifier` interfaces + `SetNotifier` (auth: welcome, account: deletion confirmation, tribe: member added, throttled to one per recipient per day). Brevo is listed as a processor in `Privacy.tsx`.
- Link images: `internal/preview` scrapes pages (Chrome TLS fingerprint via `netsafe.NewBrowserClient`, then WhatsApp/Facebook preview UAs, oEmbed). `link.RunImageBackfill` (started in `main.go`) fills `image_url` for links without one in the background, recording attempts in `image_checked_at` (retry after 7 days); changing a link's URL triggers an immediate retry. Android mirrors the extractor offline in `androidMain/.../data/PageImageExtractor.kt` (jsoup) + `OgImageFetcher.kt`, and both clients fetch an image when an image-less idea is opened.

### AI generation (`internal/ai`)
Ideas are written by the **local Ollama model only, no web search** (`service.go`, `ollama.go`, `prompt.go`). The model answers under a JSON schema imposed via Ollama `format` (title, description, category, tags, ageRange — no URL nor price, they would be invented); `parseIdeas` normalizes and salvages truncated JSON. Small CPU VPS: default `qwen3:1.7b`, `think:false` only when the model supports thinking, one generation at a time → `ErrBusy`/429, pulled and warmed at startup. Ideas are only returned; clients save the ones the user keeps. Each idea carries a short `why` (« pourquoi », in the schema); `POST /v1/ai/generate` also takes optional `count` (≤ 8) and `exclude` (titles already proposed: listed in the prompt and filtered out), used to bring a new idea when the user drops one. `expectedCategory` takes the earliest hint word of the request.

Clients follow the « Idées avec l'IA v2 » mockup (web `components/AiSheet.tsx`, opened by `useComposer().openAi({ folderId?, prompt?, childId? })`; Android `ui/AiGenerateScreen.kt`, `Screen.Ai`): a sentence to complete (« Je cherche [des activités] pour [Léo] [ce week-end], [à la maison], budget [gratuit]. » + optional detail; children come from the tribe), inspirations that fill it in cascade, a glowing tipi with rolling messages while generating, 5 ideas arriving one by one with their « pourquoi », keep / drop (a dropped one is replaced: refill of 3 with `exclude`), then the kept ones fly into the folder (default: the origin folder, else an existing folder with the generated name, else a new one; the folder picker is shared with the add flow: `components/FolderPicker.tsx` / `FolderPickerSheet`). The sentence is sent as is as the prompt (children named with their age). Sentence options, inspirations and labels are duplicated in `lib/aiRequest.ts` and `data/AiRequest.kt` (`AiRequestTest`). Model benchmark on real prompts: `go test -tags aibench -run TestBench ./internal/ai` (see `bench_test.go`).

Config is all env vars, see `backend/internal/config/config.go` (Mongo, JWT, ports, Ollama, `ADMIN_PASSWORD`).

## Clients

- **Web** (refonte « Le feu de camp », mobile-first): `src/lib/api.ts` is the single API layer (base `/v1`, relative — Vite proxy in dev, `API_URL=… npm run dev` to target another backend; same origin in prod). Types in `src/lib/types.ts`, design tokens in `src/index.css` (`@theme`), category/folder metadata in `src/lib/categories.ts`. `lib/data.tsx` (`useMyData`) caches the user's links/folders/children; `components/Composer.tsx` (`useComposer`) owns every create/edit sheet (add, idea form, folder form, AI). Routes in `App.tsx` (data router), screens in `pages/`. Lint (`npm run lint`) uses the strict React Hooks v7 rules: no synchronous setState in effects — mount sheets only when open instead of resetting them.
- **Android**: `composeApp/src/commonMain/kotlin/` — `data/` (models, `*Repository`, `ApiClient`/`AuthenticatedApiClient` over `HttpURLConnection`, `SessionManager`), `viewmodel/LinkViewModel.kt` (large, holds most app state as `StateFlow`), `ui/` (Compose screens). Navigation is state-based in `AppModern.kt`: tabs are composed on first visit and then kept alive but unplaced (`keptHidden`) while another tab or a pushed screen is shown, so returning is instant and keeps scroll — a tab's `LaunchedEffect(Unit)` therefore runs once, not on every visit (community ideas refresh via `refreshCommunityIfStale`, 5 min). The Explorer mosaic renders cards in batches of 24. Measure perf on a release build: debug Compose is ~2× slower. All repositories default to `data.Backend.url` (**production** `https://tribbae.fr`); a debug build can target a local backend with `./gradlew :composeApp:assembleDebug -Ptribbae.apiUrl=http://10.0.2.2:8080` (`BuildConfig.API_URL`, applied in `MainActivity`; cleartext is allowed for 10.0.2.2/localhost only). Offline-first: local creation then sync, backend is source of truth.

Idea age (`ageRange`) stays a string server-side but is entered with an age picker (bands = Explorer filter bands, shortcuts from the tribe's children ages, precise steppers by 6 months under 2 years) and always written in one canonical form (« 3–6 ans », « 18 mois – 3 ans », « 10 ans et + », « Tous âges »); parsing/formatting live in `frontend/src/lib/age.ts` and `composeApp/.../data/AgeRange.kt` (keep in sync; `AgeRangesTest` pins the cases). Legacy free-text values are still read.

Explorer default order « À la une » is a weighted shuffle reseeded every 6 h (`rotationScore`, FNV-1a + u^(1/weight), weight from likes and freshness), implemented identically in `frontend/src/lib/links.ts` and `ui/ExploreScreen.kt` — keep them in sync (`androidUnitTest/.../RotationScoreTest.kt` pins reference values from the web).

Folder customization (« Personnaliser » screen: cover illu/uni/tipis/pois/rayures/photo, 9 illustrated banners, description, key date + countdown, « Pour qui » children, view mode, sort, pinned) lives in `folder.proto` (`UpdateFolderRequest` uses `optional` fields + `set_child_ids` so older clients don't wipe them; `internal/folder/style.go` validates; key date/children/pinned are hidden from non-tribe viewers). Logic is duplicated in `frontend/src/lib/folderStyle.ts` and `composeApp/.../data/FolderStyle.kt` (auto illustration from name/date, countdown labels — `FolderStyleTest` pins the cases). Banner drawings are generated from the design mockup into `frontend/src/components/FolderBannerArt.tsx` and `composeApp/.../ui/campfire/FolderBannerShapes.kt` (pastel ones take the folder color's bg/mid); folder icon paths and the 9-color palette (bg/mid/ink) are duplicated in `lib/categories.ts` and `ui/campfire/FolderCover.kt` / `Campfire.kt` / `Theme.kt`.

Screen transitions follow the « Transitions & navigation » mockup on both clients: opening an idea morphs its card into the detail (web: View Transitions via React Router `viewTransition`, names `idea-visual`/`idea-title`, `lib/transitions.ts` + `index.css`; the detail shows the cached/preview link instantly so the morph has a target. Android: `Screen.Detail.origin` from `CardOrigins` (recorded by `IdeaVisual`) + `heroFrom` in `AppModern.kt`, `LocalOpenProgress` delays the detail body; predictive back shrinks it to 92 %). Drilling (detail → folder « Rangée dans ») slides in from the right while the previous page recedes 30 % and dims, and the source idea is outlined in the folder. Tab changes fade in with a 26 px slide in the tab's direction. Durations/easings live in `ui/Transitions.kt` and `index.css`; keep them in sync.

« Ma tribu » follows the « Ma tribu v2 » mockup on both clients (web `pages/Tribe.tsx`, Android `ui/ProfileModernScreen.kt`): the tribe seated around the campfire (accounts then children, 5 seats max then « +N »), tabs « Le foyer » (tribe accounts, pending invitations with « Relancer » = re-invite, children cards → child sheet with birthday, their folders and « Des idées pour … » opening the AI) and « Le cercle » (folder collaborators grouped by person — owner-only on the backend, so only my folders are manageable), « Inviter autour du feu » (foyer = tribe email invitation, cercle = add collaborator to chosen folders, or share a folder link), « Notre année en idées » and the settings list. Ring positions, circle grouping, year stats and per-child idea counts are duplicated in `lib/tribe.ts` and `data/TribePage.kt` (`TribePageTest`).

Adding an idea follows the « Ajouter une idée v2 » mockup on both clients: a multi-step sheet (start from the clipboard link / a link / writing / a photo / the AI → the link is read and its findings shown → « Où on la range ? » with 3 suggested folders and their reasons, a folder picker with search and inline creation, category, age bands, public toggle → « C'est rangé ! » celebration with the eve reminder). Web `components/AddFlow.tsx` (opened by `useComposer().openAdd`, « Plus de détails » falls back to `LinkFormSheet`), Android `ui/AddFlowScreen.kt`. Suggestions, « qui la verra » and age bands are duplicated in `lib/addFlow.ts` and `data/AddFlow.kt` (`AddFlowTest`). Photos (« Une photo », and « Mettre une photo » in the idea form) are uploaded to the backend: see Photos below.

Dark mode « La veillée » follows the « Mode sombre · palette veillée » mockup (in `Tribbae — Refonte UI.html`): a warm dark, no shadows, depth from lighter surfaces (page `#1C1411` → card `#282019` → sheet/nav `#33281F`) and thin borders; categories, folder colors and avatars get dark tints with light inks; terracotta and prune keep their color, links turn `#F0855E`; « soleil » discs become orange halos; photos at 90 % brightness. The preference (« Apparence » Jour / Soir / Auto in Ma tribu, default Auto = follow the device) is kept on the device. Web: `lib/theme.ts` + `public/theme.js` (applied before first paint, a separate file because the CSP forbids inline scripts) set `<html data-theme>`; `index.css` redefines the `@theme` tokens under `:root[data-theme="dark"]` (plus `card`, `link`, `on-solid`, `sky`, `ground`, `blush`, `peach` tokens; `.surface-raised` for sheets, `.nav-bar` for the bottom bar). Use tokens (`bg-card`, not `bg-white`; `var(--color-…)` in inline styles; folder and avatar colors are CSS variables in `lib/categories.ts`) so both themes work. Android: `ui.Appearance` (pref saved by `AndroidStorage`, system mode from `MainActivity`) and the palette in `ui/Theme.kt` are getters that pick the light or dark value (`CardColor`, `SheetColor`, `OnDark` for text on prune/terracotta, `OnSolid`, `PhotoVeil`, `SunDisc`, `SoleilPanel`, pastel pairs `BlueBg/BlueInk`…); use them instead of `Color.White` or literals. The legacy `App.kt` screens (`Modern*Screen`, `SettingsScreen`, `LinkListScreen`) are not wired and were not themed.
