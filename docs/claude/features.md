# Sharing, rights and community features

Business rules for tribe, circle, publishing, moderation and gift lists. Read before touching ownership, visibility or invitations.

- Tribe (`internal/tribe`, `tribe.proto`): accounts of one family share everything (ideas, folders, children). `tribe.Service.Peers(userID)` = the user + members with `sharing=true`; it is injected via `SetTribePeers` into the link, folder and child services and every ownership check must go through it (`isPeer`/`ownedByTribe`), never `owner_id == userID` alone. Joining is by invitation only (`internal/tribe/invitations.go`, `tribe_invitations`): `AddTribeMember` emails `SITE_URL/invitation#<token>` (hashed token, 7 days, one per tribe and address, resend after 10 min, members + pending ≤ 12) and answers the same whether the address has an account or not; `AcceptTribeInvitation` requires the signed-in account to use the invited address (the link proves it receives that inbox), `GetTribeInvitation` is public. A new member sees the tribe immediately but their own content joins only after they confirm (`sharing`). Web `pages/Invitation.tsx` (token kept in sessionStorage while signing in), Android `ui/InvitationDialog.kt` + `MainActivity.extractInviteToken`. Publishing (idea or folder visibility, moving an idea into a public folder) stays author/owner-only. One tribe per account (unique index on `members.user_id`); without a tribe document the tribe is virtual and named after the account. Ideas are always signed with the author's account name; the tribe name is only for « La tribu … » (home, Ma tribu). Clients mirror the peer set (web `useMyData().peers`, Android `LinkViewModel.isTribePeer`).
- Email verification (`internal/auth/verify.go`, `email_verifications`: hashed token, 24 h, one per account, resend after 1 min): the welcome email carries `SITE_URL/verifier-email#<token>`; `POST /v1/auth/email/verify` is public (the link proves the inbox), `POST /v1/auth/email/resend` and `GET /v1/auth/me` (`emailVerified`, also in login/register/reset responses) need a session. A password reset or an accepted tribe invitation also verifies the address. Until verified (`users.email_verified_at`, existing accounts included, admin seeded verified) the server refuses with `FailedPrecondition` « email address not verified » to publish (idea or folder turning public, idea created in/moved into a public folder — already-public content stays editable), invite into the tribe and add a collaborator: `auth.RequireVerifiedEmail` is injected via `SetEmailCheck` (link, folder) and `SetEmailVerifier` (tribe). Web: session `emailVerified` refreshed by `refreshAccount` (launch + tab focus), `components/VerifyEmailBanner.tsx` in `AppLayout`, `pages/VerifyEmail.tsx`. Android: `SessionManager.emailVerified`, `LinkViewModel.emailVerified`/`refreshAccount` (resume), `ui/EmailVerification.kt` (banner on home, `VerifyEmailDialog` from `MainActivity.extractVerifyToken`, `PublishLockedNote` on the public toggles); the offline sync leaves a refused publication pending (`waitingForVerification`) instead of failing.
- Folder share link: `POST /v1/folders/{id}/share` returns the existing link and creates one only if there is none, so a link already sent keeps working; `DELETE /v1/folders/{id}/share` (`RevokeShareToken`) cuts it at once. Owner only; `shareToken` is sent to the owner alone. « Couper le lien » in `ShareFolderSheet` on both clients.
- Circle invitations (`internal/folder/invitations.go`, `folder_invitations`, `folder.proto` `…CircleInvitation`, routes `/v1/circle/invitations`): the owner invites an address (account or not, same answer either way) to some of their folders with a role; the email links to `SITE_URL/invitation-cercle#<token>` (hashed token, 7 days, one invitation per owner and address — inviting again adds the folders, a new email only after 10 min, ≤ 30 pending, inviting needs a verified address); `GetCircleInvitation` is public, `AcceptCircleInvitation` requires the invited address, adds the account as collaborator (role from the invitation) and verifies its address; deleting a folder removes it from invitations. Both clients now invite through it (`Tribe.tsx` `CircleInviteForm`, `ShareFolderSheet` on both, Android `LinkViewModel.inviteToCircle`); `AddCollaborator` is kept only for older app versions; it emails the added account (`mail.CollaboratorAdded`, link to `SITE_URL/dossiers/{id}`, throttled in memory to one per folder and 5 per recipient per day). Web `pages/CircleInvitation.tsx`, Android `ui/CircleInvitationDialog.kt` + `MainActivity.extractCircleToken`.
- Moderation (`internal/moderation`, `moderation.proto`, `ModerationService`): anyone signed in can report an idea, a comment or an account (`POST /v1/reports`, reason spam/inappropriate/harassment/other + details ≤ 500, one open report per reporter and content, 20 a day; the target's title/text is kept in `target_summary`) — each new report emails the admin account (`mail.Reports(auth.AdminEmail)`, kind and reason only). Blocking (`/v1/blocks`) is one-way: the blocker no longer gets the blocked account's ideas (community and new lists), comments and public folders — filtered in the link, comment and folder handlers through `SetBlocked(modSvc.BlockedSet)`, one query per request. Admin (`AdminService.ListReports` / `ResolveReport`, `/v1/admin/reports`): `dismiss`, `remove` (idea → private + `hidden`, which can no longer be republished — FailedPrecondition « idea removed by moderation » — nor exposed by a public folder; `Link.hidden` tells the author; comment → deleted; account → suspend) or `suspend` (`users.suspended_at`: login refused with PermissionDenied « account suspended », `auth.SessionValid` rejects existing sessions, public ideas become private + hidden, public folders private, comments hidden; an admin account can't be suspended and `EnsureAdminAccount` lifts a suspension set in the database). Only what the reporter can see is reportable (`SetAccess(linkSvc.CanView, tribeSvc.Peers)`: anything else answers NotFound, so no private title lands in a report), never one's own tribe; a decision closes every open report of the same content. `reports` and `blocks` are in the GDPR export and deletion. Clients: on someone else's idea (outside the tribe) the « … » menu offers « Signaler l'idée », « Signaler <auteur> » and « Bloquer <auteur> », each comment from someone else has a flag; report sheet web `components/ReportSheet.tsx`, Android `ui/ReportSheet.kt` (reasons and labels duplicated in `lib/moderation.ts` ↔ `data/Moderation.kt`, `moderation.test.ts` ↔ `ModerationTest`); « Comptes bloqués » in Réglages (`BlockedSheet` on both); the admin queue is web only (`components/AdminReports.tsx` in `/admin`).
- Comments: one deletion rule on server and both clients — the comment's author, or the idea's author and their tribe (`comment.Service.SetTribePeers`). Deleting an idea also deletes its likes and comments.
- Gift lists « Offrir une idée » (`internal/folder/gifts.go`, `gift_reservations`, `folder.proto` `…Gift…`): a folder with `giftReservations` (« C'est une liste de cadeaux » in the folder form) lets anyone reserve its Cadeau ideas, and **nobody ever sees who offers what** (not other givers, not the creator or her tribe): ideas carry `giftStatus` relative to the reader (empty, `reserved`, `bought`, or `mine`/`mine_bought`). From the share link without an account: first name + email (`POST /v1/share/{token}/links/{id}/reservation`); the reservation stays `pending` 2 h (TTL index) until the emailed link `SITE_URL/offrir#<token>` confirms it, and the same link marks it bought or releases it (`POST /v1/gifts/manage`, public; 5 reservations per email and list per day + IP limit). With an account: reserved at once, from the link or the idea screen (`POST /v1/links/{id}/gift`, needs `CanView`). Emails: the creator gets « Une surprise se prépare » (no detail, at most hourly), other givers get « Un cadeau s'est libéré ». The tribe can reset all reservations (`DELETE /v1/folders/{id}/reservations`). Reservations go with the idea, the folder and the account (export + deletion, by `user_id` or email). Web `components/GiftList.tsx` (share page), `GiftPanel.tsx` (idea screen), `pages/OfferGift.tsx` (`/offrir`); Android `ui/SharedGiftList.kt` (a folder opened from its share link, in `PublicFolderScreen`: same list, sheet and no-account flow; the shared folder is fetched with the session so `mine` statuses come back, pending reservations of the device are kept by `LinkRepository.pendingGifts`; the emailed `/offrir` link opens in the browser), `ui/GiftPanel.kt` (idea screen); states, progress, filters and refusal messages duplicated in `lib/gifts.ts` ↔ `data/Gifts.kt` (`gifts.test.ts` ↔ `GiftsTest`).
- « C'est fait » (`internal/link/done.go`, `link_dones`, `link.proto` `…LinkDone…`): one gesture to say an idea was lived (outing done, recipe cooked, book read, gift bought), as many times as it is redone, with an optional memory (day, who was there among the tribe's accounts and children, rating 0–5, note ≤ 280, photo sent through `POST /v1/photos`, « À refaire »). One `link_dones` row per time; `Link` carries reader-relative `doneCount`, `lastDoneAt` (noon UTC of the day: only the date counts, clients read its first 10 characters), `redo`, `donePromptDismissed`, and `doneFamilies`. Routes: `POST /v1/links/{id}/done` (`MarkLinkDone`), `PATCH`/`DELETE /v1/links/{id}/done/{doneId}`, `GET /v1/links/{id}/done`, `POST /v1/links/{id}/done-prompt/dismiss` (« Pas cette fois »), `GET /v1/done/summary?year=` (« Notre année en idées », counted by the server since a redone idea counts each time), `ListLinks` `status=all|todo|done`; all need a session. **Rights**: marking, editing and dismissing = the idea's tribe (`isPeer`) and EDITOR collaborators of its folder; a memory is edited or removed only by the tribe of whoever marked it. **Reading**: the idea's tribe and the folder's members (any role) only — an outside account, Explorer and the share link get empty fields (`Stats.DoneVisible`, loaded in two queries per batch by `loadDones`). On a public idea `doneFamilies` is the number of distinct tribes that did it (`tribe_key` = smallest peer id when marked), sent from 5 up, else 0; no name, no photo. **Gift lists**: a Cadeau idea in a `giftReservations` folder never goes through `link_dones` (`MarkLinkDone` → FailedPrecondition, the purchase stays `giftStatus`), so the surprise holds. `doneOn` is never in the future (with the margin of time zones ahead of UTC) nor before 2000; 50 marks per account per day; memories go with the idea, and with the account (export `doneMemories`, deletion, and the account pulled from others' « qui était là »); photo cleanup also keeps photos cited by `link_dones.photo_url`. Folder `sort` gains `todo` (« À faire d'abord »). Clients: web `components/Done.tsx` (`DoneProvider` in `AppLayout`: tick on cards, memory sheet « Comment c'était ? », celebration, toast with « Annuler », `MemoryCard`, `ProgressRing`, `DonePrompt`), Android `ui/Done.kt` (`DoneController` through `LocalDone`, `DoneHost` at the root; long press on a card opens the menu). Cards show the tick only inside the tribe's folders (`done` prop / parameter), never in Explorer. Labels per category, date format, `awaitingConfirmation` (dated outing or activity passed the day before or earlier, not done, not dismissed → « Fait ? » badge and folder banner), `folderProgress` (activities, outings, recipes, books; null under 3 or in a gift list), « À faire d'abord » sort, filters and year labels are duplicated in `lib/done.ts` ↔ `data/Done.kt` (`done.test.ts` ↔ `DoneTest`) and `lib/tribe.ts` ↔ `data/TribePage.kt`. Android only: the day after a dated outing at 10:00 one local notification asks « Vous êtes allés à … ? » (`data.DonePrompts` in `Reminders.kt`, `NotificationHelper.reconcile`, actions « Oui, on y était » → detail on the memory sheet via `MainActivity` extra `done_link_id`, « Pas cette fois » → `ReminderReceiver`; switch « Me demander si on y est allés » in Réglages, `ReminderPrefs.askDone`); marking is online-only on Android, like the Like. The tribe activity feed is out of scope.
- Shared shopping list « Les courses » (`internal/shopping`, `shopping_lists`, `shopping.proto` `ShoppingService`): one list per tribe, keyed by `tribe.Service.Household` (the stored tribe's id, or the account alone; every member has it from the day they join, like the tribe's shared content). The server keeps decisions only — menu (`link_id`, `servings`, `added_by`, `added_at`), free items (`id`, label, quantity, aisle, `added_by`), checked line keys (`key → by, at`), typed quantities and hand-picked aisles per product key, `aisle_order` (default order when empty; the setting screen comes later), `pantry` (« on en a », kept from one list to the next), `removed` recipe lines, `shopper_id` / `shopping_since` (« X est en magasin », dropped after 2 h; no push notification). Line and product keys are computed by the clients (same logic web ↔ Android); a free item's line key is `item:<id>`. `GET /v1/shopping?sinceVersion=` answers `unchanged` when the client is up to date; `POST /v1/shopping/ops` applies a batch of ops in order (`menu_add`/`menu_servings`/`menu_remove`, `item_add` with an optional client id so a replayed op adds nothing, `item_update`/`item_remove`, `check`/`uncheck`, `quantity`, `aisle`, `aisle_order`, `pantry_have`/`pantry_out`, `remove`/`restore`, `shopping_start`/`shopping_stop`, `finish` = empty the basket (checked lines and bought free items) keeping menu and pantry, `clear` = new list keeping pantry and aisles); a refused op refuses the whole batch, and the document is written with an optimistic `version` check (retried), so the last op on a line wins. `menu_add` needs a Recette idea the user can see (`CanView`). Read returns each menu recipe's title, image, ingredients and `base_servings` (the idea's `servings`, 4 when unset); a recipe the reader can no longer see is left out, a deleted one leaves the menu, and one marked « C'est fait » after it was added is `cooked` (faded) that day and leaves the menu the next day (Europe/Paris). An account joining a tribe brings its own list (merged, then deleted). GDPR: the household list is exported; deletion removes the account's own list, pulls its items and checks from the tribe list, blanks its `added_by` on the menu, and deletes the tribe list when the tribe disappears. `Link.servings` (0 = unset; an update sending 0 keeps the stored value for older clients).
